# CodingBot 0.5.0 — hook 통합 e2e 사이클 설계

- 작성일: 2026-05-01
- 베이스: `v0.4.0` (commit `5c5d961`)
- 사이클 가치 분류: **C2 — 검증 자동화 (hook 분기까지 확장)**
- 범위: 0.4.0 fake_claude 인프라 위에 (a) runner-only S4 시나리오, (b) hook subprocess 통합 트랙(transcript JSONL fixture + hook harness + S5 + JudgeTimeout 2건 + JudgeError 1건). 운영 코드는 `llm_judge._call` 진입부 fault-inject 분기 1블록으로 한정.
- 비범위: cassette/record-replay, judge 캐싱, metrics export, 배포(D), risky_tool PreToolUse 차단 e2e (`hook_integration` 트랙 정착 후 별도 사이클).

## 1. 동기

0.4.0이 닫은 자동 e2e는 runner ↔ fake_claude ↔ handoff ↔ state 경로뿐이다. hook 분기는 여전히 **단위 + subprocess 단위 회귀**로만 검증되고, 다음 분기들은 통합 회귀가 비어 있다:

- **S4 (연속 abnormal 2회 → exit 2)** — runner 안전망의 가장 강한 보장. 0.2.0에서 도입됐지만 e2e가 없다. 시나리오 1건이면 닫힘.
- **S5 (stop signal 활성 상태에서 Stop hook 호출)** — `state.set_stop_signal()` 후 Stop hook이 `_allow_stop("stop_signal_or_limit_active")`로 빠지는지. cli `stop` ↔ hooks 통합 보장.
- **JudgeTimeout / JudgeError 분기** — `auto_approve._defer_to_user("llm_timeout"/"llm_failed")` 와 `handoff_or_continue._allow_stop("llm_timeout"/"llm_failed")` 분기. 0.3.0에서 카운터/예외는 단위로 검증됐으나, **실제 hook subprocess가 환경상 timeout/error 상황에서 같은 결정을 내리는지**는 비어 있음. 안전망 신뢰의 마지막 1마일.

0.5.0은 hook subprocess를 진짜로 띄우는 통합 e2e 트랙을 도입해 위 4분기를 닫는다.

## 2. 핵심 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| hook 발화 방식 | **B. subprocess + env 기반 fault injection** | A(in-process)는 hook 프로세스 경계 손실. C(fake `anthropic` 모듈)는 PYTHONPATH/PATHEXT 의존 — 0.4.0에서 폐기한 PATH shim과 동일 함정. |
| hook 호출 진입점 | `sys.executable -m codingbot.hooks.<name>` (subprocess) | Windows PATHEXT 비의존. PYTHONPATH 자동 상속. fake_claude가 정착시킨 패턴과 일관. |
| fault-inject 위치 | `llm_judge._call` 함수 진입부 | 외부 API 호출 직전. 두 경로(`evaluate_tool_safety`, `classify`)가 모두 통과. 1블록으로 양 hook 분기 동시 커버. |
| fault-inject 트리거 | env `CODINGBOT_FAULT_INJECT` ∈ {`judge_timeout`, `judge_error`} | env 미설정 시 분기 미진입. prod 영향 0. |
| fault-inject 의미 | 즉시 `JudgeTimeout` / `JudgeError` raise. 부수 효과 없음. | 조용한 fallback 금지 — 잘못 켜져도 시끄럽게 실패. |
| transcript JSONL 시뮬레이션 | fixture factory가 dict 리스트 → 임시 파일 (Claude Code session schema). hook이 실제 파일 read | 0.1.2 transcript 정공법과 동일 schema. |
| 시나리오 트랙 | runner 트랙(0.4.0 `test_runner_loop.py`) + hook 트랙(신규 `test_hook_integration.py`) | runner와 hook은 호출 경로가 다르므로 분리. e2e_auto 마커 공유. |
| 마커 | 기존 `e2e_auto` 재사용 | 새 마커 추가 안 함. |
| 운영 코드 변경 범위 | `llm_judge.py`에 fault-inject 1블록(약 8라인). 다른 운영 모듈 무수정. | "바꿀 이유가 명확한 곳에만 제한적 허용" (사용자 결정) — timeout/error 경로는 외부 API에 의존해 e2e가 본질적으로 비결정적이라는 명확한 구조적 이유. |

## 3. 컴포넌트 명세

### 3.1 `codingbot/llm_judge.py` 변경

#### 3.1.1 추가 분기

`_call(system, user)` 진입 직후, `_client()` 호출 이전:

```python
def _call(system: str, user: str) -> str:
    fault = os.environ.get("CODINGBOT_FAULT_INJECT")
    if fault == "judge_timeout":
        raise JudgeTimeout("fault inject: judge_timeout")
    if fault == "judge_error":
        raise JudgeError("fault inject: judge_error")
    cfg = config.load()
    ...  # 기존 코드
```

- 분기 위치: 함수 첫 줄. `cfg = config.load()` 위.
- 동작: 두 키 중 하나면 즉시 raise (메시지에 `fault inject:` prefix). 그 외 값은 무시(분기 미진입).
- prod 영향: env 미설정이면 분기 0. 설정 시 외부 API 호출 자체가 일어나지 않음(비용 0).
- 외부 인터페이스 변경 없음.

#### 3.1.2 회귀 (단위)

- `test_llm_judge_fault_inject_timeout`: `monkeypatch.setenv("CODINGBOT_FAULT_INJECT", "judge_timeout")` → `evaluate_tool_safety(...)` → `JudgeTimeout` raise.
- `test_llm_judge_fault_inject_error`: 동일하게 `judge_error` → `JudgeError` raise.
- `test_llm_judge_fault_inject_unknown_value`: `CODINGBOT_FAULT_INJECT="bogus"` 설정 + (API 호출 미발생을 위해 `_client` monkeypatch로 빈 응답) → 분기 미진입. (또는 unknown value는 단순히 미진입 = 기존 경로 유지를 단위로만 확인.)

### 3.2 `tests/e2e/conftest.py` 추가 fixture

#### 3.2.1 `transcript_jsonl_factory`

- 시그니처: `transcript_jsonl_factory(messages: list[dict]) -> Path`.
- 입력 dict는 인간 친화 dict (예: `{"role": "user", "text": "..."}` 또는 `{"role": "assistant", "text": "..."}`). factory가 Claude Code session schema(top-level `type`, `message.content` blocks)로 변환해 임시 JSONL을 생성.
- 반환: 생성된 JSONL의 절대경로 (tmp_path 산하). 자동 정리.
- 0.1.2에서 정착된 `iter_messages` schema와 일치하도록 다음 형태 emit:
  - user: `{"type": "user", "message": {"role": "user", "content": [{"type": "text", "text": "..."}]}}`
  - assistant: `{"type": "assistant", "message": {"role": "assistant", "content": [{"type": "text", "text": "..."}]}}`

#### 3.2.2 `hook_env`

- 시그니처: `hook_env(**overrides) -> dict[str, str]`.
- 기본: `os.environ` 사본 + `CODINGBOT_HOME=tmp_codingbot_home의 경로`.
- overrides로 `CODINGBOT_FAULT_INJECT`, `ANTHROPIC_API_KEY` 등 주입.
- `tmp_codingbot_home` fixture(이미 존재)와 협력 — hook이 같은 home을 보도록 보장.

### 3.3 `tests/e2e/hook_harness.py` (신규)

stdlib only. 약 60~80 LOC.

#### 3.3.1 공개 API

```python
def run_pre_tool_use(
    stdin_dict: dict,
    env: dict[str, str],
    timeout: float = 30.0,
) -> HookResult: ...

def run_stop_hook(
    stdin_dict: dict,
    env: dict[str, str],
    timeout: float = 30.0,
) -> HookResult: ...
```

- 각각 `subprocess.run([sys.executable, "-m", "codingbot.hooks.auto_approve"], ...)` 또는 `...handoff_or_continue` 실행.
- stdin: `json.dumps(stdin_dict)` (utf-8). stdout/stderr: 캡처. cwd: 프로젝트 루트(상속).

#### 3.3.2 `HookResult` 데이터클래스

| 필드 | 타입 | 의미 |
|---|---|---|
| `exit_code` | int | hook 종료 코드 (정상이면 항상 0) |
| `stdout` | str | hook stdout 전체 |
| `stderr` | str | hook stderr 전체 |
| `decision` | dict \| None | stdout이 JSON이면 파싱, 아니면 None ( = `_allow_stop` 또는 `_defer_to_user` 분기 시그널) |

`decision is None`은 명시적 의미 — Stop hook의 `_allow_stop` 또는 PreToolUse hook의 `_defer_to_user`. `decision is not None`이면 `decision.get("decision")`이 `"approve"` 또는 `"block"`.

### 3.4 시나리오 명세

#### 3.4.1 S4 — 연속 abnormal 2회 → exit 2 (runner 트랙)

위치: `tests/e2e/test_runner_loop.py`.

시나리오 JSON: `{"name": "abnormal_repeat", "steps": [{"exit_code": 2}, {"exit_code": 2}]}`.

검증:
- `runner.run(prompt)` 반환값 `2`.
- stderr (capsys 또는 capfd)에 `"연속 비정상 종료"` 포함. (state에는 abnormal exit 카운터가 없음 — 0.6.0+ 후보로 별도.)
- lock 파일 정리 (`paths.lock_file().exists() == False`).
- handoff 파일 부재.
- `state.read()["cycles_this_run"]` == 2 (두 step 모두 실행됨).

#### 3.4.2 S5 — stop signal 활성 상태에서 Stop hook (hook 트랙)

위치: `tests/e2e/test_hook_integration.py`.

준비:
- `paths.stop_signal_file().touch()` (cli stop과 동일 메커니즘 — `state.set_stop_signal` 함수는 존재하지 않음. stop signal은 파일 존재 = active).
- transcript_jsonl_factory로 짧은 transcript 생성 (assistant 마지막 텍스트는 임의 — 처리 전에 should_stop 분기).
- stdin: `{"transcript_path": "<생성된 jsonl>"}`.

검증:
- `result.decision is None` (빈 stdout = `_allow_stop`).
- `state.read()["stop_allow"]` +1.
- exit_code == 0.

#### 3.4.3 S6 — JudgeTimeout / PreToolUse (hook 트랙)

준비:
- `CODINGBOT_FAULT_INJECT=judge_timeout` (hook_env override).
- `ANTHROPIC_API_KEY=fake-key` (lazy import 통과용).
- transcript: assistant 1건 (heuristic 분류 ambiguous하도록 짧고 중립).
- stdin: ambiguous tool — 예 `tool_name="Bash", tool_input={"command": "echo hello | tee out.txt"}` (heuristic이 risky/safe 어느 쪽으로도 분류 안 되는 경계 케이스).

검증:
- 사전 검증: 동일 stdin을 fault-inject 없이 실행하면 heuristic 분류가 `"ask"`(judge 호출로 빠지는 케이스)임을 단위 회귀로 확인 (선택).
- `result.decision is None` (=`_defer_to_user`).
- `state.read()["judge_timeout_total"]` +1, `judge_call_total` +1.

#### 3.4.4 S7 — JudgeTimeout / Stop (hook 트랙)

준비:
- 동일 fault-inject env.
- transcript: heuristic이 `is_clearly_done`/`is_clearly_continuing` 어느 쪽도 매칭 안 되는 본문 (judge 분류로 흘러야 함).

검증:
- `result.decision is None` (=`_allow_stop("llm_timeout")`).
- `state.read()["judge_timeout_total"]` +1.

#### 3.4.5 S8 — JudgeError / Stop (hook 트랙)

준비:
- `CODINGBOT_FAULT_INJECT=judge_error`.
- 나머지 S7과 동일.

검증:
- `result.decision is None`.
- `state.read()["judge_error_total"]` +1.

PreToolUse 쪽 JudgeError는 단위 회귀로 이미 충분 — 통합에서는 S8 1건으로 분기 도달만 확인.

### 3.6 호환성

- `llm_judge` 외부 인터페이스 변경 없음 (`evaluate_tool_safety`, `classify`, 예외 클래스 동일).
- env `CODINGBOT_FAULT_INJECT` 미설정 시 모든 동작 0.4.0과 비트 동일.
- state.json schema 변경 없음.
- public API breaking change 없음.

## 4. 테스트 계획

### 4.1 회귀 추가 합계

| 트랙 | 추가 건수 |
|---|---|
| 단위 (`tests/unit/test_llm_judge.py`) | 2~3 (fault-inject) |
| e2e runner | 1 (S4) |
| e2e hook integration | 4 (S5/S6/S7/S8) |
| harness 자체 단위 (`tests/e2e/test_hook_harness.py` 또는 e2e_auto 내 sanity) | 1~2 |

총 +8~10. 0.4.0 시점 182 → 190 내외 예상.

### 4.2 wall time 목표

- e2e_auto 합계: < 60초 (0.4.0 < 30초 → hook subprocess 5건 추가, 각 평균 2~3초).

### 4.3 결정성 보장

- 모든 fault-inject은 env 키만 사용 — 외부 API/네트워크/시간에 무의존.
- subprocess 호출은 `sys.executable -m`으로 PATH 무의존.
- transcript JSONL은 tmp_path 격리.

## 5. 리스크 / 가드

| 리스크 | 가드 |
|---|---|
| fault-inject 분기가 prod에 노출됨 | env 키 미설정 시 분기 미진입(테스트로 검증). 메시지 prefix `fault inject:`로 운영 로그에서 즉시 식별 가능. |
| hook subprocess가 hang | `subprocess.run(timeout=30)` 강제. 초과 시 테스트 실패. |
| Windows에서 `python -m codingbot.hooks.X` 경로 실패 | `sys.executable` 사용으로 venv/system python 모두 호환. 0.4.0에서 fake_claude도 동일 패턴 사용. |
| transcript schema drift | 0.1.2 정공법 schema 그대로 emit. transcript factory와 `iter_messages` 사이 schema 변경 시 양쪽 동시 갱신 필요 — spec drift 체크 항목에 추가. |
| heuristic이 의도치 않게 ambiguous tool을 분류해버림 | S6에서 사용하는 tool 입력은 사전에 단위 회귀로 `verdict == "ask"`임을 확인 (Task 단계에서). |
| `tmp_codingbot_home` fixture와 hook subprocess 환경 불일치 | `hook_env` fixture가 `CODINGBOT_HOME`을 같은 tmp 경로로 강제. |

## 6. 비범위 / 후속

- **risky_tool 차단 e2e** (secret/install/priv 분기를 hook 트랙으로): 0.5.x polish 또는 0.6.0.
- **cassette/record-replay**: judge 캐싱 도입 후 자연스럽게 결합 가능. 별도 사이클.
- **judge 캐싱 (B2)**: 0.5.0 카운터로 ROI 평가 후 별도 사이클.
- **metrics export (E)**: 별도.
- **배포(D)**: 별도.
