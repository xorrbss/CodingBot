# CodingBot 0.3.0 — 관측(metrics) 사이클 설계

- 작성일: 2026-05-01
- 베이스: `v0.2.0` (commit `3434973`)
- 사이클 가치 분류: **A — 신뢰성/안전성 (관측 강화)**
- 범위: state.json 카운터 세분화 + `JudgeTimeout` 분리 + `codingbot status` 출력 섹션화
- 비범위: 절대 누적 카운터, prometheus exporter, judge 캐싱, e2e 자동화, 외부 dashboard

## 1. 동기

0.2.0은 (a) 시크릿 / (c) 패키지 / (d) 권한 카테고리와 chain 우회 차단, llm_judge timeout, runner CLI 부재 처리를 추가했다. 그러나 **그 안전망이 실제 사용 중에 얼마나 발동하는지** 확인할 수단이 없다. 현재 `state.json`은 `auto_approve_count`/`auto_continue_count` 두 카운터뿐이라:

- llm_judge가 몇 번 호출되는지 / 그중 timeout이 몇 번인지 알 수 없다 → API 비용/latency 가시성 부재.
- approve/defer가 heuristic으로 처리됐는지 LLM으로 처리됐는지 구분 불가 → 룰 커버리지 평가 불가.
- handoff hook의 continue / handoff / unstuck / allow_stop 분포를 알 수 없음.

0.3.0은 이 가시성을 닫는다. 외부 의존 0, 새 모듈 0, 의존 그래프 변경 없음.

## 2. 핵심 결정

| 항목 | 결정 |
|---|---|
| 데이터 저장 위치 | 기존 `state.json` 안의 카운터 키 추가 (별도 metrics 파일/DB 도입 안 함) |
| 누적 정책 | per-run 누적. `start_cycle`이 0으로 리셋 (기존 정책 동일). 절대 누적은 YAGNI |
| 카운터 origin 분리 | judge source(heuristic / llm / rule) 축으로 카운터 분리. outcome × source 곱셈은 폭발하므로 outcome만 분리하거나 source만 분리 — 분기 가치 큰 쪽만 적용 (§3.3) |
| `JudgeError` timeout 식별 | 별도 서브클래스 `JudgeTimeout(JudgeError)`. 호출자는 `except JudgeTimeout: ... except JudgeError: ...` 두 줄로 분기 |
| timeout 매핑 방식 | `_call` 내부에서 `anthropic.APITimeoutError` (lazy import 그대로) 인지 isinstance 분기 후 `JudgeTimeout` raise |
| 기존 카운터 호환 | `auto_approve_count`, `auto_continue_count` 유지. 신규 카운터는 *추가* 레이어 (mutually consistent) |
| CLI 노출 | `codingbot status` 확장. 신규 `stats` subcommand 도입 안 함 (KISS) |
| 출력 가독성 | status 출력 섹션 4개로 구분 (Status / Cycle / Decisions / Judge / Config) |
| 의존 그래프 | 변경 없음 (state는 여전히 config/logger/paths만 의존) |

## 3. 컴포넌트 변경 명세

### 3.1 `state.py` — 신규 카운터

#### 3.1.1 `_initial_state` 확장

기존 4 키에 신규 8 키 추가. 모두 `0`으로 초기화하여 status 출력에서 `n/a` 분기를 만들지 않는다.

```python
def _initial_state() -> Dict[str, Any]:
    return {
        "cycle_started_at": ...,
        "cycles_this_run": 0,
        # 기존 (호환 유지)
        "auto_approve_count": 0,
        "auto_continue_count": 0,
        # 신규: PreToolUse decision source
        "auto_approve_by_heuristic": 0,
        "auto_approve_by_llm": 0,
        "auto_defer_by_rule": 0,
        "auto_defer_by_heuristic": 0,
        "auto_defer_by_llm": 0,
        # 신규: Stop hook outcome
        "stop_block_continue": 0,
        "stop_block_handoff": 0,
        "stop_block_unstuck": 0,
        "stop_allow": 0,
        # 신규: judge call telemetry
        "judge_call_total": 0,
        "judge_timeout_total": 0,
        "judge_error_total": 0,
    }
```

#### 3.1.2 신규 `record_*` 함수

`_increment(key)` 패턴 그대로. 외부 호출자(hook)에서 명시적으로 호출.

```python
def record_auto_approve_by(judge: str) -> None:
    """judge ∈ {'heuristic','llm'}"""
    _increment(f"auto_approve_by_{judge}")

def record_auto_defer_by(judge: str) -> None:
    """judge ∈ {'rule','heuristic','llm'}"""
    _increment(f"auto_defer_by_{judge}")

def record_stop_outcome(outcome: str) -> None:
    """outcome ∈ {'block_continue','block_handoff','block_unstuck','allow'}"""
    _increment(f"stop_{outcome}")

def record_judge_call() -> None:
    _increment("judge_call_total")

def record_judge_timeout() -> None:
    _increment("judge_timeout_total")

def record_judge_error() -> None:
    _increment("judge_error_total")
```

**검증 정책**: `judge`/`outcome` 인자가 unknown 값이면 `ValueError` raise (호출자 측 버그 조기 발견). 카운터 키 자유 조합으로 인한 오타 방지.

### 3.2 `llm_judge.py` — `JudgeTimeout` 분리

#### 3.2.1 클래스 추가

```python
class JudgeError(Exception):
    """LLM 호출/파싱 실패. 호출 측에서 안전 폴백."""

class JudgeTimeout(JudgeError):
    """API 호출 타임아웃. JudgeError의 특수 케이스."""
```

`isinstance(JudgeTimeout, JudgeError)` 관계 유지 — 기존 `except JudgeError`는 그대로 둘 다 잡음 (하위 호환).

#### 3.2.2 `_call` 분기

```python
def _call(system: str, user: str) -> str:
    cfg = config.load()
    try:
        resp = _client().messages.create(...)
    except Exception as e:
        import anthropic  # lazy (이미 _client 안에서 import됨, 여기서 재 import 비용 없음)
        if isinstance(e, anthropic.APITimeoutError):
            raise JudgeTimeout(f"API call timed out after {cfg.judge_timeout_secs}s") from e
        raise JudgeError(f"API call failed: {e}") from e
    ...
```

**대안 검토**: `JudgeError(kind=...)` 필드 방식은 호출 측이 `if e.kind == 'timeout':` 분기를 strings로 비교해야 해서 타입 안전성 약함. 서브클래스 채택.

### 3.3 `hooks/auto_approve.py` — 카운터 호출 추가

#### 3.3.1 `_approve` / `_defer_to_user` 시그니처 보강

기존 `judge` 인자(이미 받고 있음)를 카운터 분기에 활용.

```python
def _approve(reason: str, judge: str) -> None:
    state.record_auto_approve()  # 기존 (호환)
    state.record_auto_approve_by(judge)  # 신규
    logger.info("auto_approve", decision="approve", judge=judge, reason=reason)
    print(json.dumps({"decision": "approve", "reason": reason}))

def _defer_to_user(why: str, judge: str) -> None:
    state.record_auto_defer_by(judge)  # 신규
    logger.info("auto_defer_to_user", judge=judge, reason=why)
```

#### 3.3.2 judge 호출 telemetry

llm_judge 호출 직전/직후/예외 분기에서 카운터 증가:

```python
state.record_judge_call()
try:
    result = llm_judge.evaluate_tool_safety(...)
except llm_judge.JudgeTimeout as e:
    state.record_judge_timeout()
    logger.warn("llm_timeout", hook="auto_approve", error=str(e))
    _defer_to_user("llm_timeout", judge="llm")
    return 0
except llm_judge.JudgeError as e:
    state.record_judge_error()
    logger.warn("llm_api_error", hook="auto_approve", error=str(e))
    _defer_to_user("llm_failed", judge="llm")
    return 0
```

**근거**: `record_judge_call`은 호출 시도 횟수(=총 비용 단위), `timeout`/`error`는 그중 실패 분포. approve 성공시는 별도 카운터 없음 (call_total - timeout - error로 유추 가능, YAGNI).

#### 3.3.3 stop_signal 분기

`if state.should_stop(): _defer_to_user("stop_signal_active", "rule")` — 기존 코드. `_defer_to_user` 안에서 `record_auto_defer_by("rule")` 자동 호출되므로 추가 변경 없음.

### 3.4 `hooks/handoff_or_continue.py` — outcome 축 카운터

#### 3.4.1 `_block` / `_allow_stop` 보강

기존 코드는 이미 `outcome` 인자를 `_block`이 받고 있으므로(`_block(reason, judge, outcome)`) 그대로 활용. 단, logger outcome 어휘(`request_handoff` 등)와 카운터 키 어휘(`block_handoff`)가 달라 inline dict로 매핑을 한 곳에 둔다:

```python
_OUTCOME_TO_COUNTER = {
    "continue": "block_continue",
    "request_handoff": "block_handoff",
    "unstuck": "block_unstuck",
}

def _block(reason: str, judge: str, outcome: str) -> None:
    state.record_auto_continue()  # 기존 (호환)
    state.record_stop_outcome(_OUTCOME_TO_COUNTER[outcome])  # 신규
    logger.info("stop_hook", outcome=outcome, judge=judge)
    print(json.dumps({"decision": "block", "reason": reason}))
```

**outcome 매핑 표** (`_OUTCOME_TO_COUNTER`의 의도 명세):

| logger outcome | 카운터 키 |
|---|---|
| `continue` | `block_continue` |
| `request_handoff` | `block_handoff` |
| `unstuck` | `block_unstuck` |

dict 미스 시 `KeyError`가 즉시 노출되어 새 outcome 추가 시 매핑 누락이 조기 발견된다.

`_allow_stop`은:

```python
def _allow_stop(why: str, judge: str = "rule") -> None:
    state.record_stop_outcome("allow")
    logger.info("stop_hook", outcome="allow_stop", judge=judge, reason=why)
```

#### 3.4.2 judge 호출 telemetry

`auto_approve`와 동일 패턴:

```python
state.record_judge_call()
try:
    verdict = llm_judge.classify(msgs)
except llm_judge.JudgeTimeout as e:
    state.record_judge_timeout()
    logger.warn("llm_timeout", hook="handoff_or_continue", error=str(e))
    _allow_stop("llm_timeout", judge="llm")
    return 0
except llm_judge.JudgeError as e:
    state.record_judge_error()
    logger.warn("llm_api_error", hook="handoff_or_continue", error=str(e))
    _allow_stop("llm_failed", judge="llm")
    return 0
```

**source axis는 의도적으로 분리하지 않는다**: stop hook은 outcome이 더 중요한 신호 (continue가 잘 작동하는지). source는 logger에서 검색 가능하므로 카운터로 굳히지 않음 (YAGNI).

## 6. 위험 / 트레이드오프

### 6.1 카운터 누락 (가장 큰 위험)

`record_*`가 hook 분기마다 명시적으로 호출되므로 **새 분기가 추가되거나 기존 분기를 수정할 때 호출을 빠뜨릴 수 있다**. 회귀 테스트가 분기마다 1건씩 보장하고 있어 코드 수정 시 실패하면 카운터 누락이 드러난다. 이 외 추가 방어는 하지 않는다 (decorator/aspect는 over-engineering).

### 6.2 status 출력 비대화

신규 섹션 4개로 출력이 ~25줄. 가독성은 섹션 분리로 유지되지만, 향후 카운터가 더 늘면 별도 `codingbot stats` 분리 검토. 0.3.0에서는 KISS로 status 통합.

### 6.3 `JudgeTimeout` 분기 누설

`except JudgeError`로만 묶여 있는 호출자가 있으면 timeout 카운터가 0으로 굳음. 이번 사이클의 두 hook 모두 `except JudgeTimeout` → `except JudgeError` 순으로 명시 분기하도록 회귀로 못 박음. 향후 새 호출자가 추가될 때 같은 패턴 강제는 spec/리뷰 책임.

### 6.4 `_initial_state`에 12개 0 키 = state.json 비대화

각 키 ~30 byte → 추가 ~360 byte. 무시 가능.

### 6.5 outcome 매핑의 mental model

`logger outcome` 문자열(`request_handoff`)과 카운터 키(`stop_block_handoff`)가 다른 어휘. 매핑 dict를 `_OUTCOME_TO_COUNTER`로 명시화하여 한 곳에서 관리.

## 8. Out of scope / 후속

- **e2e 자동 검증 골격** (0.4.x 후보): fake `claude` CLI subprocess + transcript JSONL 생성기. 별도 사이클.
- **judge 캐싱** (보류): 분류 고착 위험. 측정 데이터 (0.3.0이 만드는 것) 기반으로 ROI 평가 후 결정.
- **절대 누적 카운터 / 외부 metrics export**: 본 사이클 가시성으로 충분한지 사용자 피드백 받은 후 결정.
- **judge source axis × stop outcome 곱셈 카운터**: 의미 있는 신호로 판단되면 추가 검토. 현재는 logger 검색으로 충분.
